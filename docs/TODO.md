# TODO — غير مُنفَّذ فعليًا (بصراحة تامة)

القاعدة المتبعة في هذا المشروع: أي زر أو ميزة في الواجهة إما تعمل فعليًا بمنطق حقيقي، أو غير موجودة أصلاً. لا توجد أزرار "مزيَّفة" في أي مكان. هذا الملف يسرد كل ما طلبته المواصفة الأصلية ولم يُنفَّذ بعد، مع سبب كل بند وما يحتاجه إكماله.

## تكاملات خارجية حقيقية (تحتاج بيانات اعتماد فعلية لا تتوفر هنا)

- **بوابة دفع إلكتروني حقيقية.** `payments.method` يدعم `online` في الـ schema، لكن لا يوجد تكامل فعلي مع أي بوابة دفع (Paymob، Fawry، إلخ). المواصفة نفسها نصّت على عدم تنفيذ هذا بدون بيانات API فعلية. **للإكمال:** اختيار بوابة، الحصول على مفاتيح API، تنفيذ webhook لتأكيد الدفع وتحديث حالة الفاتورة تلقائيًا.
- **WhatsApp Notifications الفعلية.** الإشعارات الحالية (`notifications` table) داخلية فقط (تظهر في النظام). لا يوجد إرسال فعلي عبر WhatsApp Business API. **للإكمال:** حساب WhatsApp Business API (عبر Meta أو مزوّد مثل Twilio)، طبقة إرسال في `src/lib/` تُستدعى من نفس نقاط إنشاء الإشعار الحالية.
- **تكامل API فعلي مع شركات الشحن.** `POST /api/orders/[id]/shipment` يسجّل اسم شركة الشحن ورقم التتبع يدويًا فقط. لا استدعاء API فعلي لأي شركة شحن (بوسطة، أرامكس، مصر إكسبريس). **للإكمال:** بيانات اعتماد API لكل شركة، طبقة تكامل موحَّدة (Integration Layer) تستبدل الإدخال اليدوي دون تغيير شكل جدول `shipments`.
- **قارئ باركود فعلي.** حقل `barcode` موجود ومُستخدَم في البحث النصي، لكن لا يوجد مسح فعلي بالكاميرا/بهاردوير قارئ. **للإكمال:** مكتبة مسح باركود عبر كاميرا المتصفح (مثل `@zxing/library`) في صفحة Picking.

## ميزات تحتاج عملاً إضافيًا (ممكنة تقنيًا، لم يتسع الوقت)

- **تصدير PDF للفواتير.** حاليًا الفاتورة تُعرَض في الواجهة فقط (JSON عبر API، وعرض HTML في `/customer/billing`). لا يوجد زر "Download PDF" فعلي. **للإكمال:** مكتبة توليد PDF من HTML (مثل Puppeteer أو `@react-pdf/renderer`) في route جديد `/api/invoices/[id]/pdf`.
- **دعم إنجليزي كامل للواجهة (Arabic First + English Support).** الواجهة عربية بالكامل حاليًا (RTL). البنية تدعم اللغتين تقنيًا (كل النصوص في مكوّنات React منفصلة عن المنطق)، لكن لا يوجد نظام i18n فعلي (مثل `next-intl`) ولا زر تبديل لغة. **للإكمال:** تركيب `next-intl`، استخراج كل النصوص العربية الحالية لملفات ترجمة، إضافة نسخة إنجليزية موازية، زر تبديل LTR/RTL ديناميكي.
- **اختبارات آلية شاملة.** يوجد اختبار smoke test يدوي كامل (موثَّق في `docs/TESTING.md`) يغطي كل دورة حياة الطلب فعليًا وناجح بالكامل، لكن لا توجد اختبارات آلية (Jest/Vitest) تُشغَّل عبر `npm test`. **للإكمال:** تركيب Vitest، تحويل سيناريوهات `docs/TESTING.md` إلى اختبارات آلية.
- **إدارة عدة مخازن من الواجهة.** الـ schema يدعم Multi-Warehouse بالكامل (`warehouses`, `zones`, `racks`, `shelves`, `bins` كلها مرتبطة بـ `warehouseId`)، والبيانات التجريبية تضم 3 مخازن فعلاً، لكن لا توجد صفحة إدارة في `/admin` لإنشاء/تعديل مخزن أو هرم المواقع (Zone→Rack→Shelf→Bin) من الواجهة — فقط عبر API أو seed script مباشرة. **للإكمال:** صفحات CRUD في `/admin/warehouses`.
- **AI Forecasting.** لم يبدأ العمل عليه إطلاقًا — يحتاج تصميم منفصل بالكامل (بيانات تاريخية كافية غير متوفرة في نظام جديد أصلاً).
- **Rate Limiting فعلي على الـ API.** المواصفة طلبت Rate Limiting كجزء من الأمان؛ الكود الحالي يعتمد على حماية RBAC + input validation (Zod) في كل route، لكن لا يوجد تحديد عدد طلبات فعلي (مثل بمكتبة `@upstash/ratelimit` أو middleware مخصص). **للإكمال:** middleware في `src/middleware.ts`.
- **Email Verification فعلي.** التسجيل ينشئ الحساب ويسجّل الدخول فورًا بدون تحقق من البريد الإلكتروني. **للإكمال:** إرسال رابط تحقق (يحتاج مزوّد بريد مثل Resend/SendGrid) وحقل `emailVerifiedAt` في جدول `users`.
- **Forgot/Reset Password.** غير مُنفَّذ — يحتاج نفس مزوّد البريد أعلاه لإرسال رابط إعادة التعيين.

## قرارات تصميم واعية (ليست نقصًا، لكن تستحق التوضيح)

- **SQLite بدل PostgreSQL** — قرار بيئي مؤقت، انظر `docs/ARCHITECTURE.md` لتفاصيل الانتقال.
- **JWT مخصص بدل NextAuth/Auth.js** — المواصفة اقترحت Auth.js كخيار، لكن تنفيذ JWT+cookie مباشر أعطى تحكمًا كاملاً بشكل الجلسة بدون تعقيد إعداد مزوّد خارجي لمشروع بهذا الحجم. التبديل لـ Auth.js ممكن لاحقًا دون تغيير جداول `users`.
- **خطة تسعير واحدة نشطة (`isDefault`) بدل عدة خطط متزامنة.** الـ schema يدعم عدة صفوف في `pricing_plans`، لكن الواجهة والمنطق الحالي يستخدمان خطة افتراضية واحدة فقط. دعم خطط متعددة (Starter/Business/Pro كخطط منفصلة فعليًا في قاعدة البيانات بدل عرض تسويقي فقط) يحتاج منطق اختيار خطة لكل عميل — لم يُطلَب صراحة في المواصفة كسلوك، فقط كعرض في الصفحة الرئيسية (وهو منفَّذ).
